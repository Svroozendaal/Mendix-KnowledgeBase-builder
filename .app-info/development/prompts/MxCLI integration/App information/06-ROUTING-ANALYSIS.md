# Routing Analysis — mxcli Impact Assessment

## Two Types of Routing

### A) Repo-Level Navigation (`.app-info/ROUTING.md`)
Guides agents to the right folder in the repository. References the current pipeline diagram.

### B) KB Routing Files (generated inside each knowledge base)
Generated by `run-kb-compose.ps1` inside `mendix-data/knowledge-base/`:

| File | Purpose | Data Source |
|------|---------|-------------|
| `ROUTING.md` | Main KB navigation hub with module index | Module list + quality metrics |
| `routes/by-entity.md` | Entity CRUD lifecycle index | `domain-model.json` entities + flow action flags |
| `routes/by-flow.md` | Flow index with tier, calls, evidence links | `flows.json` flows/nodes/calls |
| `routes/by-page.md` | Page index with provenance, datasources | `pages.json` pages + `shownByPage` from ShowPageActions |
| `routes/cross-module.md` | Dependency matrix, association links, hub/leaf classification | `flow.calls[].targetFlowName` + `associations[].parentEntity/childEntity` |
| `routes/keyword-index.md` | Keyword-to-artifact map | Entity/flow/page name tokenization |

## Phase 1: No Changes Required

All KB route tables are built from intermediate data structures in `run-kb-compose.ps1` (lines 1275–1474):

- `entityLookup` / `entityModule` / `entityLifecycle` — from `domain-model.json`
- `flowList` / `flowFacts` — from `flows.json`
- `pageFacts` / `shownByPage` — from `pages.json` + flow ShowPageActions
- `crossModuleEdges` — from `flow.calls[].targetFlowName` cross-module matching
- `associationRows` — from `domain-model.json` associations

Since mxcli produces the **same JSON v2.0 schema**, these data structures populate identically. The composer reads the same JSON, builds the same structures, produces the same routing files.

### Route-by-route confirmation

| Route file | Data consumed | mxcli impact |
|---|---|---|
| `by-entity.md` | Entity names, modules, attributes, access rules, flow action flags for CRUD lifecycle | **None** — same JSON fields |
| `by-flow.md` | Flow qualified names, kind, module, nodes, calls, retrieve/decision/showPage/mutation actions | **None** — same JSON fields |
| `by-page.md` | Page names, modules, roles, parameters, dataSources, clientActions, navigationProvenance | **None** — same JSON fields |
| `cross-module.md` | Cross-module flow call edges + cross-module association links | **None** — same JSON fields |
| `keyword-index.md` | Entity/flow/page name tokenization | **None** — names from same JSON |
| `ROUTING.md` | Module list, categories, complexity scores, quality metrics | **None** — same JSON fields |

### Copilot KB validation (`kb.routes.ts`)
Only checks for `READER.md` and `ROUTING.md` file existence + counts module directories. Does not parse routing content. **Unaffected.**

## Phase 2–3: Enhancement Opportunities

While routes work unchanged in Phase 1, mxcli enables **richer routing** in later phases:

### 1. Richer Cross-Module Dependencies
**Current:** `cross-module.md` only tracks flow-call edges (`flow.calls[].targetFlowName`) and association links.

**With mxcli:** The `refs` catalog table captures ALL reference types:
- `call` — flow calls another flow
- `use` — page uses a flow as data source
- `reference` — entity referenced in access rule XPath
- `contains` — structural containment

Plus `SHOW CALLERS/CALLEES TRANSITIVE` gives full transitive call chains.

**Impact:** `cross-module.md` dependency matrix could show page→flow, entity→accessRule, and transitive dependencies — not just direct flow calls.

### 2. Explicit Entity Lifecycle (CRUD)
**Current:** Entity lifecycle in `by-entity.md` is **inferred** from text pattern matching (`Get-TextEntityMentions` on node labels/details) combined with `Get-ActionFlags` (HasCreate, HasRead, etc.). This is approximate — it checks if a flow mentions an entity name AND has a create/read/update/delete action, but can't confirm the action targets that specific entity.

**With mxcli (Full mode):** The `activities` table provides `EntityRef` per activity, giving **deterministic** entity-to-action mapping.

**Impact:** `by-entity.md` CRUD columns become export-backed rather than inferred. Fewer false positives and no missed relationships.

### 3. Widget-Based Page Routing (New)
**Current:** No widget-level routing exists.

**With mxcli (Full mode):** The `widgets` catalog provides every widget instance with type, entity binding, and attribute binding.

**Impact:** New `routes/by-widget.md` route file mapping widgets → pages → entities.

### 4. Workflow Routing (New)
**Current:** No workflow routing exists (workflows are counted but not detailed).

**With mxcli:** Full workflow metadata including activities, user tasks, decisions, and microflow calls.

**Impact:** New `routes/by-workflow.md` route file indexing workflows with their steps, assigned user tasks, and connected microflows.

### 5. Navigation-Based Page Provenance
**Current:** Page entry provenance in `by-page.md` is derived from flow ShowPageActions and limited `navigationProvenance` data. Many pages show "Unknown" provenance.

**With mxcli:** `navigation_profiles` + `navigation_menu_items` + `navigation_role_homes` catalog tables provide complete navigation structure.

**Impact:** `by-page.md` entry provenance becomes complete — every navigation entry point is captured, reducing Unknown gaps.

### 6. Integration Routing (New)
**Current:** No OData or external integration routing.

**With mxcli:** `odata_services`, `odata_clients`, `business_event_services`, `database_connections` catalog tables.

**Impact:** New `routes/by-integration.md` route file mapping external service connections.
